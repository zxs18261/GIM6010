# 本项目的Skill使用说明

Skill是AI在某类任务中遵循的流程，不是电机参数数据库，也不会自动扩大修改、烧录或带电测试权限。

## 如何触发

正常描述任务时，允许AI根据Skill的描述自动选择。需要确定流程时，在消息开头显式写`$skill-name`。多个Skill可以同时指定，AI应在开始工作前说明本轮使用哪些Skill以及各自作用。

示例：

```text
$stm32-foc-debugging $diagnosing-bugs
分析开环能转但进入电流环后过流的问题，只分析，不修改代码。
```

## 如何知道正在使用什么

AI开始工具操作前应给出简短声明：

```text
本轮使用：
- stm32-foc-debugging：判断FOC阶段、安全门控和观测量
- diagnosing-bugs：建立复现信号、候选原因和单变量实验
```

如果Skill改变了工作顺序或暂停任务，也应说明原因。最终交付应能从结构看出相应流程，但“输出风格像某Skill”不能替代明确声明。

## 当前主要Skill

### `stm32-foc-debugging`

可自动触发。用于STM32 FOC移植、PWM/ADC/编码器/校准、开环及三环控制、过流、不转、方向和速度上限。它会先判断最高通过阶段，区分只读、改代码、编译、烧录和带电测试，并要求观察量、通过标准、停止条件和证据路径。

推荐：

```text
$stm32-foc-debugging 判断当前工程进入电流环前还缺哪些验证，只分析。
```

### `diagnosing-bugs`

可自动触发。用于不转、抖动、过流、数据跳变、回归和实时性能异常。它要求先建立能准确反映现象的反馈信号，再最小化、列出3～5个可证伪假设、一次改变一个变量，最后回归并清理临时插桩。

推荐：

```text
$diagnosing-bugs 分析VOFA命令后电源过流，先给复现和证伪步骤。
```

### `domain-modeling`

可自动触发。用于统一电机轴/输出轴、电角度/机械角、Uq/Iq/转矩、装配校准/机械臂归零等术语，以及维护[项目术语](CONTEXT.md)和ADR。它可能先指出词义冲突，再讨论代码。

### `writing-plans`

多步骤实现前使用。它先列精确文件、顺序和验证，再开始修改；适合从开环进入电流环、调整通信协议或移植另一FOC库。

### `embedded-review`

用户要求评审嵌入式改动时使用。重点检查中断、DMA、共享数据、内存安全、外设时序、Flash、硬件接口和C/C++陷阱。它不能替代真实编译和台架验证。

### `writing-for-agents`

创建或维护Skill、`AGENTS.md`、`CLAUDE.md`和代理规则时使用。它要求主入口简洁、按分支渐进披露、单一事实来源和可检查的完成标准。

### `domain-modeling`与`writing-for-agents`的边界

前者决定项目词语的准确含义；后者决定AI文档如何组织和触发。具体电机参数仍写入[项目配置档案](project-profile.md)，不写进这两个Skill。

### `handoff`

不会自动触发，必须显式调用。它把本次对话压缩成下一会话的临时交接，并链接现有权威文档，不复制一套新事实。

```text
$handoff 下一会话继续进行电流采样标定和电流环准备。
```

### `team-brainstorm`

粗略想法尚未形成要求时使用。例如开始设计机械臂应用层归零方案时，先整理目标、约束、选项、风险和待确认项；已经是明确的单项代码修复时不必使用。

## 常用组合

- FOC阶段分析：`stm32-foc-debugging`。
- FOC异常：`stm32-foc-debugging + diagnosing-bugs`。
- 大型代码修改：`stm32-foc-debugging + writing-plans`。
- 修改后评审：`embedded-review`，再结合真实编译结果。
- 统一术语或长期决策：`domain-modeling`。
- 维护个人FOC Skill：`writing-for-agents + skill-creator`。
- 结束较长会话：显式`handoff`。

## 授权边界

自动触发Skill只改变分析和验证流程。用户说“只分析”时不得写文件；“修改代码”不等于允许烧录；“编译”不等于允许带电；任何功率级测试仍需明确硬件条件和授权。仓库文档的持续更新也服从当前请求中的更严格限制。
